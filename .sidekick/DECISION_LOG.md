# Sidekick Decision Log

Important decisions, alternatives, and reasons. Owned by Agent 1.

## Decisions

| ID | Date | Decision | Alternatives considered | Reason |
|---|---|---|---|---|
| D1 | 2026-10-21 | Four fixed agent roles; Agent 1 owns contracts/playbook/task board | Unfixed roles; shared editing of coordination files | Prevents four agents creating conflicting project structures; single shared source of truth |
| D2 | 2026-10-21 | Default branch `main`; PR-only updates; required CI; no self-approval | Direct pushes to `main` | Protects shared source of truth across four PCs |
| D3 | 2026-10-21 | `.sidekick/` files owned by Agent 1; Agent 4 owns integration evidence files | All agents editing the same coordination files | Prevents conflicting coordination documents |
| D4 | 2026-10-21 | `convaiinnovations/laya` treated as a lead, not a guaranteed dependency | Committing to laya upfront | Availability, license, resource needs, and loading behavior not yet verified |
| D5 | 2026-10-21 | Real functionality only; no faked voice/subtitles/service/Alexa+ claims; test doubles only in tests/dev mode | Mock-heavy build | Product truthfulness requirement; verified claim levels |
| D6 | 2026-10-21 | Session state isolated by explicit session ID; thread-safe/session-scoped storage; no global singleton | Global singleton | Cross-session leakage risk; two-session isolation must be proven |
| D7 | 2026-10-21 | Core brain implemented in Python (FastAPI + pydantic v2); Node is not installed on this PC | TypeScript/Node backend | The only runtime available here is Python 3.13; the decision model (`laya`) is a Python package anyway. The HTTP contract is language neutral for Agent 2/3 |
| D8 | 2026-10-21 | The real decision model is `convaiinnovations/laya` (Apache-2.0, self-hosted), loaded lazily with a hard timeout; the deterministic catalog matcher is the fallback and is always reported | Bedrock / hosted LLM | Verified available on Hugging Face, no API key, non-generative (no hallucinated output), typed questions map 1:1 onto the contract. Model choice can be revisited in Phase 5 |
| D9 | 2026-10-21 | Control verbs (cancel/pause/resume/status/confirm/reject) are resolved by a deterministic grammar and are *not* offered to the model | Letting the model choose control intents | Measured with the real model: with control intents in the answer space it chose a control more often than the right capability (42% tool accuracy). Removing them raised the capability accuracy and made control turns instant |
| D10 | 2026-10-21 | Corrections are split into preceding/residue by discourse markers *before* the model is called; the model only sees the residue | Letting the model resolve the correction | Measured with the real model: it chose the stale destination ("YouTube" for "no wait, open Spotify") and scored 0.03 on `is_correction`. The markers are reliable and general |
| D11 | 2026-10-21 | The model's destination answer is only used above a confidence floor of 0.7; the catalog matcher fills it otherwise | Trusting the model's argmax | The model answers a destination with 100% accuracy when it is sure, but invents one with ~0.3 confidence when the utterance has no destination |
| D12 | 2026-10-21 | `decision_model.fallback_used` is true whenever the interpretation was *not* produced by the configured model (unavailable, timeout, invalid output, low confidence, or a deterministic control) | Reporting only model failures | Otherwise a response could imply the model did the work when it did not |
| D13 | 2026-10-21 | A running action that the adapter cannot stop becomes `paused` with `error.code = cancellation_unsupported`, never `cancelled` | Reporting it as cancelled | The work may still be running; reporting success would be a lie |
| D14 | 2026-10-21 | A plain "and" is only a segment separator when both sides resolve to *different* capabilities | Splitting on every "and" | "echo hello and goodbye" is one request; splitting it would drop the second half |
| D15 | 2026-10-21 | A trailing correction marker ("echo hello instead") supersedes the previous *request*, not the other segments of the same turn; a marker in the middle supersedes both | One rule for every marker position | With one rule, "cancel that and echo hello instead" superseded the cancel before it could run. The two positions mean different things and are now handled separately |
| D16 | 2026-10-21 | A full stop followed by whitespace is a sentence boundary | Splitting on every full stop | "Start that game. Actually, pause the music first." is two requests; "5.5 minutes" is one |
| D17 | 2026-10-21 | The decision model may not name a capability the utterance does not mention; the deterministic matcher decides which capabilities the utterance supports and the model chooses between them | Trusting the model's argmax | Measured with the real model: on an answer space it is not calibrated for, it answered "order dinner for me" and "xyzzy plugh" with "read my notes" *and reported success*. Its confidence is meaningless here, so the answer must be anchored to the utterance. The model keeps the job of choosing between plausible capabilities and of picking the destination |
| D18 | 2026-10-21 | A destination is used only when the utterance mentions it; the model chooses between the mentioned ones | A confidence floor on the model's destination | The model answers a destination with 100% accuracy when there is one and invents one with ~0.3 confidence when there is not - and the confidence is not calibrated. Mentioning is the reliable test |
| D19 | 2026-10-21 | Capability aliases match by content words, with a light stem and a specificity order | Substring matching | "show me my notes" matched the browser launcher's "show me" and "list my timers" did not match "list timers". The matcher now compares content words, so a specific alias beats a generic verb |
| D20 | 2026-10-21 | An unsupported request answers "I do not have a capability for that yet" and lists what *is* possible, in human words | "I did not catch which action you want" with a list of tool names | The old answer did not distinguish "I did not understand" from "I cannot do that", and it was the same for every unsupported request |
| D21 | 2026-10-21 | "What can you actually do?" is answered from the catalog and is checked before the correction handling | Letting the model answer it | The word "actually" is a correction marker, so the question would have been read as a correction. The inventory also has to name the *whole* product, including the capabilities the browser client runs |
| D22 | 2026-10-21 | Capabilities the browser client runs are declared in `sidekick/client_capabilities.json` and marked `execution_target: "client"`; the core plans them and waits for the client to report the outcome | Declaring them executable in the core | The product is bigger than the server. The core must not claim it played music. The declaration is additive: nothing breaks if the file is absent |
| D23 | 2026-10-21 | `web.search` and `reminder.set` are real core capabilities | - | A search and a scheduled reminder are core work: both run locally with no credential. A search is explicitly *not* a booking and the spoken line says so |
| D24 | 2026-10-21 | The first model call gets its own, longer time budget | One timeout | The first call also builds the checkpoint (~30 s on this CPU), so it was reported as a model timeout and the product silently fell back |
| D25 | 2026-10-21 | A test run may not have side effects: `webbrowser.open` and `webbrowser.get` are replaced for the whole session, and the audit harness stubs the browser unless `--real-browser` is given | Stubbing the browser only where a test needs it | The audit harness and two integration tests opened real windows while the audit ran. A test run must not touch the machine it runs on |
| D26 | 2026-10-21 | No loose "did you mean": the answer lists what the product can do; only a single typo in a *service name* is resolved | Suggesting the nearest capability by word overlap | "find a restaurant" suggested "play a movie" - the noun changed and nothing deterministic knows that. A wrong suggestion is worse than none |
| D27 | 2026-10-21 | A client-executed action carries a 120 s deadline and fails with `client_timeout` if the client never reports | Leaving it pending until the client answers | A capability the app was supposed to run must not hang forever; the failure is explicit |
| D28 | 2026-10-21 | Only a client-executed capability can be completed by the client; completing a server capability is a conflict | Allowing any action to be completed | Otherwise a client could claim work the server did, which is exactly the false-success bug the anchor fixed |
